# Модель ограниченной очереди

## Назначение

Модель описывает очередь ёмкости `N=2` на Spin/Promela. В исправной модели
процесс `Environment` моделирует помещение, извлечение и отказ запросов.
Отдельного мьютекса, производителя и потребителя в текущем исходном коде нет:
в модели работает один процесс `Environment`.

## Состояние

- `count` — число элементов, учитываемых моделью.
- `q[2]` — ячейки очереди; `0` означает пустую ячейку, `1` и `2` — ID элементов.
- `err` — признак ошибочного состояния.
- `pending1`, `pending2` — принятые элементы, ещё не извлечённые из очереди.
- `draining` — фаза обязательного опустошения после достижения полной ёмкости.
- `full_reject_done` — признак, что единственный отказ при полной очереди уже смоделирован.

Идентификаторы `1` и `2` не дублируются в очереди. При помещении элемента
устанавливается соответствующий `pending`-флаг. При извлечении этого ID
флаг сбрасывается. Поэтому L1 относится именно к принятым элементам, а не
к любому запросу enqueue, включая отклонённые запросы.

## LTL-свойства

| ID | Формула | Смысл |
|---|---|---|
| S1 | `[] (count <= N)` | Нет переполнения |
| S2 | `[] (count >= 0)` | Нет отрицательного счётчика |
| S3 | `[] (!err)` | Нет ошибочного состояния |
| L1 | `[] ((pending1 -> <> !pending1) && (pending2 -> <> !pending2))` | Каждый принятый элемент в итоге извлекается |
| L2 | `[] (count > 0 -> <> (count == 0))` | Непустая очередь в итоге становится пустой |

## Допущение, обеспечивающее L2

В обычной ограниченной очереди наличие свободного места и возможность извлечения
сами по себе не гарантируют, что недетерминированный выбор ветвей когда-либо
выберет извлечение. Флаг `-f` в Spin обеспечивает справедливость процесса, но
не справедливость выбора ветвей внутри процесса.

Поэтому текущая модель явно ограничивает поведение после заполнения:

1. При `count==N` устанавливается `draining=1`.
2. При `draining==1` ветвь помещения новых элементов отключена.
3. Допускается один отказ запроса при полной очереди; затем
   `full_reject_done=1` отключает повторение этой ветви.
4. Извлечение остаётся доступным до достижения `count==0`.
5. При `count==0` сбрасываются `draining` и `full_reject_done`.

Следовательно, доказательство L2 относится к модели с такой политикой
дренирования. Оно не доказывает L2 для произвольной очереди, в которой после
заполнения разрешено бесконечно выбирать отказ или продолжать приём новых
элементов.

## Багованная модель и контрпримеры

В `queue_buggy/queue.pml` дополнительный процесс `Buggy` при `count==N`
выполняет атомарно `err=1` и `count=count+1`. Это создаёт контрпримеры для
S1 и S3. Актуальные файлы следов:

- `queue_buggy/traces/S1.trail`
- `queue_buggy/traces/S3.trail`

Для воспроизведения следа скопируйте нужный файл в `queue.pml.trail` в каталоге
`queue_buggy` и выполните `spin -t -p queue.pml`. Полная последовательность
команд приведена в `commands.txt`.

## Важное ограничение

Модель отслеживает два фиксированных ID, а не неограниченный поток уникальных
сообщений. Она запрещает повторное помещение ID, пока предыдущий элемент с
этим ID не извлечён. Поэтому L1 доказывает liveness для двух отслеживаемых
слотов/идентификаторов в данной конечной модели.
